# Численный эксперимент

## 1. Постановка и план

Выполняй эксперименты самостоятельно в рамках поставленной задачи и обычных
разрешений среды. Кратко сообщи план перед содержательным запуском; отдельное
согласование каждого небольшого опыта не требуется. Порядок работы и сохранения
контекста задан в `AGENTS.md`; актуальные результаты и следующий шаг — в
`PROJECT_STATUS.md`.

- Вопрос и проверяемая гипотеза; какой результат её опровергнет.
- Задачи (R1–R5 и/или ID уравнений) и причина выбора: режим, сложность, геометрия.
- Для исследования сходимости — один изменяемый параметр (n, Nt, dx, tail_eps, …), остальные зафиксированы.
  При сравнении разных задач явно перечислить сопутствующие различия. Полный `asdict(config)`
  и тип бюджета: `RemizovConfig(n)` (4/4), `make_verification_config(n)` (8/5)
  или другая явно описанная конфигурация.
- Метрики:
  - E∞ = max|f − y_exact| на фиксированной сетке (датасет — `np.linspace(-1, 1, 33)`; R1–R5 — 257 точек на [−2, 2]);
  - E∞ / max|y|;
  - log2(E_n / E_2n) только для успешных пар;
  - время решателя и процесса, применения S, узлы квадратуры, пиковая сетка, RSS.
- Заранее: число попыток и критерий остановки. Не скрывать повторы и подстройку после результата:
  если нужна новая конфигурация, оформить отдельную серию с обоснованием, сохранив исходные отказы.

## 2. Оценка ресурсов

- T = `compute_truncation_T`; d_max = max(2√(a_upper·T/n), 2·B·T/n); ширина = (x_max − x_min) + 2n·d_max.
- Точки = ceil(ширина/dx) + 1 для каждого dx до dx_initial/2^max_spatial_refinements; сравнить с max_work_grid_points.
- Верхняя граница применений S: n × (сумма Nt по уровням) × (число уровней dx).
- По оценке стоимости выбрать и записать подходящие ресурсы и критерии остановки.
  Для затратных запусков полезен подпроцесс с watchdog по образцу `bounded_run` из
  `diagnostics/remizov_n4_followup.py`; учитывать, что существующие драйверы имеют свои
  параметры и могут требовать адаптации под новую задачу.
- Исторические ориентиры при n=4 и бюджете 8/5: F0005 ≈ 30 с, F0006 ≈ 23 с;
  F0000 и F0007 не завершились за 45 с. Значения 45 с / 512 МиБ относятся к тем сериям,
  не задают универсального лимита и не доказывают несходимость метода.
- Фиксировать число потоков BLAS и одновременных worker-процессов; для сопоставимых
  замеров использовать одинаковые настройки и учитывать конкуренцию за ресурсы.

## 3. Воспроизводимость и хранение

- Драйвер — в `diagnostics/`; результаты — в новый каталог `results/<тема>_<YYYY-MM-DD>[_<вариант>]/`
  (`mkdir exist_ok=False`). Изменение прежних данных допускается с возможностью восстановления по `AGENTS.md`.
- Сохранять: config, target_x, окружение (python, numpy, scipy, sympy, платформа, thread env),
  SHA-256 ядра и входных данных до и после, `asdict(RemizovResult)` каждого возврата, ресурсные сэмплы, лог.
- Отчётный скрипт читает только сохранённые файлы и решатель не вызывает.
- `external_time_limit` / `external_memory_limit` / `worker_exception` — статусы оболочки, а не failure_reason решателя.

## 4. Анализ и представление

- Таблица всех попыток: успешные, отказы с failure_reason, прерванные, not_run.
- Точность: E∞ только при success; разности квадратуры и сетки приводить отдельно, как индикаторы.
- Сходимость: порядок оценивать только по ≥ 3 успешным уровням; учитывать изменение final dx и Nt между запусками.
- Стоимость: время и счётчики работы. Для прерванных запусков сохранять известные
  wall time/RSS и явно помеченные частичные счётчики; недоступные итоговые показатели — «не определено».
- Разделять «наблюдение», «гипотеза», «не установлено»; не обобщать с одного уравнения на режим.
- Итог: ответ на вопрос, ограничения вывода, предлагаемый следующий шаг.
- После содержательной серии обновить `PROJECT_STATUS.md` в той же задаче: результаты,
  ссылки на артефакты, решения, нерешённые вопросы и следующий шаг; мелкие действия туда не переносить.
