# Решения, основания и оставшиеся развилки

Дата: 2026-10-25. Это завершённый комплект **спецификаций**, не численные
результаты и не разрешение запуска. Все текущие новые solve/MC paths/fit=0.
Статические проверки и сохранность — [verification.json](verification.json).

## Принято в проекте контракта v1

1. Общий объект — ограниченная резольвента наℝ; grid33 [-1,1], абсолютная
   E_grid≤.01, один exact. Произвольный IVP не поддерживается.
2. Главная стоимость — end-to-end **прогретый** wall выбранного метода,
   включая G/T/AST; JIT отдельно. Один worker/поток,4 повтора на задачу,
   медиана и разброс. Практическая ничья 10% плюс диапазоны, при ничьей R.
3. Основной предлагаемый результат — **A:fixed profiles / observed_fastest**.
   Reliable p≥.95 — отдельная неактивная цель; B — отдельная конфигурационная серия.
   Это не автоматическое смягчение reliable-требования:без решения пользователя
   вероятность не выдаётся за подтверждённую, а observed имеет явный scope.
4. Кандидаты R128/R256 — cubic/zero/commonT. Taper сохранён для истории,
   исключён из выбора нового главного профиля из-за известных артефактов.
   Исходный Remizov, streaming, NumPy MC не заменяют эти profile IDs.
5. Кандидаты MC0/1/2 — Numba, single1024/h128, single4096/h128, single4096/h256.
   Mean4 диагностический, не скрытый production алгоритм. Ни новые численные
   схемы, ни h512/coupling не вводятся. Более узкий h512-план прежнего аудита
   заменён этим train-пилотом, не считается выполненным.
6. Точные 40 train-ID / 40 families выбраны, все 20 ячеек покрыты. Сначала 5sentinel,
   затем только одна выбранная MC-ветка. Положительная доля MC-побед не гейт.
7. Dataset/expression/profile/source/cohort fingerprints обязательны;
   unknown≠none. Failed/missing/finite-inaccurate раздельны.
8. Признаки 253 и семейный split пригодны; старые quality-модели не становятся
   best_method моделями без новых labels. Oracle только для оценки.

Основания: [полный аудит](../ml_selector_readiness/AUDIT_REPORT.md),
`results/joint_grid100_2026-10-25/plan.json`,
`results/final_grid5_2026-10-25/analysis/comparison.csv`,
актуальные `mc_solver.py`, `mc_optimized.py`, `chernov_solver.py`.

## Цена выбора цели

По [benchmark_cost_scenarios.csv](benchmark_cost_scenarios.csv):

| Профиль | Сценарий 1000 задач×4 вызова, solver-часы |
|---|---:|
| R128 | 13.76 |
| R256 | 27.52 |
| MC0 | 14.95 |
| MC1 | 59.81 |
| MC2 | 119.61 |

Следовательно самая дешёвая пара R128+MC0 — **28.71 ч**, R128+MC2 —
**133.37 ч** solver-сценария; при R256 к этим парам добавляется 13.76 ч.
Это арифметика измеренных старых anchor times и operation scaling, **не
измеренное время нового benchmark и не гарантированный прогноз**.
Паузы, новый preprocessing, фон/thermal и изменения throughput увеличат/изменят цену.
Непосредственно измеренные сравнимые end-to-end timings ещё отсутствуют.

Для p≥.95 с 95% индивидуальной уверенностью минимум 59/59 на каждой задаче:
MC0-сценарий **220.55 ч** только MC, MC1 **882.18 ч**, MC2 **1764.22 ч**;
поправка на 1000 задач ещё дороже. Здесь нельзя обещать надёжную метку для
каждого уравнения по 4 seed. Возможен меньший бюджет с честными unknown,
но он не превращает цель reliable в достигнутую.

**Реалистичный рекомендуемый маршрут на имеющейся локальной инфраструктуре** —
этапный A/observed с проверкой цены после 5sentinel и первых 20train production.
Нет оснований обещать, что даже он поместится в одну короткую сессию.
B и полная reliable-сертификация сейчас не рекомендуются как обязательные:
требуют существенно большего бюджета, а пилот ещё не выбрал MC-профиль.
Точный доступный лимит времени/железа пользователь не задал; он не выдуман.

## Что можно решить без новых вычислений

Контракт ошибки/стоимости, семантика меток, identity, scope модели, точный выбор
train-задач, seeds, candidate configs, условные очереди и выходные schema готовы.
Проверено, какие R-клетки можно сохранить:37R128 и 5R256 в будущем пилоте;
какие 3R128 и 35R256 требуют вычисления. По 1000 — реестр недостачи готов.
Сценарии цены и CI-математика вычислены из старых файлов, без симуляции.

## Что новые данные должны решить

- Какой из R128/R256 даёт больше точных доставленных train-ответов на 40 случаях.
- Есть ли MC-профиль, показывающий полную grid33 точность при приемлемой цене;
  какая часть остатка реагирует на h при фиксированном M. Уменьшение M-noise
  подтверждено ранее, но не решает h-смещение.
- Устойчивая end-to-end стоимость на новом равном timer и hardware, разброс,
  safety/resource отказы, реальная цена оставшихся задач.
- Появятся ли MC-winner labels; если нет, нет оснований обещать их ML-распознавание.
- Можно ли подтвердить p≥.95 при отдельно выделенных независимых повторах.

## Что требует решения пользователя перед запуском

| Развилка | Рекомендация | Последствие |
|---|---|---|
| Основная цель A/observed или обязательная reliable | A/observed, CI отдельно | Не называть вывод гарантией будущего MC; reliable требует иного r/бюджета |
| Разрешение ограниченного пилота | Сначала R0+P1:38R+60MC, max compute5437 с,512MiB,1worker | Это предлагаемый cap по сценарию, не уже потраченный ресурс |
| P2 на остальных 35 | После P1, один MC-профиль,140MC; cap по измеренной цене | Ветвь может занять часы; сейчас не разрешена |
| Все три MC-кандидата без успеха | Сохранить результат; отдельно решить, нужен ли полный MC0 отрицательный контроль | Не запускать одинаковые 900 автоматически; не менять цель ради MC-побед |
| Финальный ресурс 1000×4×2 | Принять многосессионный cap / машину после P1/P2 | Если cap недостаточен, публиковать partial/узкий quality scope |
| Граница независимой оценки | Исторический семейный test с эмбарго нового протокола; новый prospective test отдельно | Ранее изученный test нельзя назвать нетронутым |
| Нужен ли B после A / aggregateMC | Пока отложить | Новое Θ/algorithm ID, дополнительные клеточные измерения и CI-поправки |

Эти согласования нужны из-за прямого ограничения текущего задания
«не запускать дополнительные численные эксперименты и обучение» и потому,
что бюджет/трактовка надёжности ещё не приняты. Это не требование skills
спрашивать разрешение на каждый технический шаг. Подготовка документов
завершена в уже разрешённом объёме; вопросы не блокировали её выполнение.

## Ответы на 10 вопросов завершения

1. **Объект:** bounded whole-line resolvent (lambda−L)y=g_R, знаки c=c_R−lambda,
   g_R=−g. Начальные условия arbitraryIVP не подставляются.
2. **Точность:** конечный допустимый f33, полная max absolute error к одному exact
   на x_j=−1+j/16; её максимум ≤.01. Это не непрерывный supremum certificate.
3. **Скорость:** wall со всей подготовкой выбранного метода, прогрев JIT отдельно,
   одинаковые условия,4 полных повтора, median/MAD/ranges, заданный tie.
4. **Профили:** R128/R256 zero/commonT; MC0/1/2 Numba; конечная пара только после
   train-пилота. Нет уже доказанного универсально точного MC-профиля.
5. **Минимальная проверка MC:** закрытый P1 на 5 train-sentinel,3 бюджета×4 seeds;
   затем максимум 35 задач одного выбранного профиля. Не повтор старой final5:
   fresh seed, новый timer, добавлен h1/256; старые результаты сохраняются.
6. **Reuse:** canonical inputs/splits/features; 100 массивов R128 и5 R256,
   MC0 для100 задач иMC1 для5 диагностических задач; старые timings только anchors,
   MCx0 только point/preflight. Исторические labels не переписываются.
7. **Недостача:** zero/commonT R для900 либо995 задач по выбранному n; MC grid33 для900,
   995 или 1000 по выбранному бюджету; однородные final timing blocks и fresh seeds
   отсутствуют по всем 1000. Точные ID в benchmark_requirements.csv.
8. **До ML:** реализовать и проверить future worker → authorizeP1 → P2/freeze
   профилей → собрать train numerics/costs →fit только train, selectvalidation →
   freezepolicy →test. Надёжный target требует отдельного CI-гейта/повторов.
9. **Если MC-win=0:** допустимость/риск R + честный abstain/подтверждённый fallback;
   сравнение с constant_R / constant_MC / oracle; никаких заявлений об обучении MC-превосходству.
10. **Согласовать:** цель observed/reliable, лимит/разрешение P1, условное P2,
    ценность полного отрицательного контроля, машину/общий cap и scope независимости.

## Как воспроизвести подготовку

Из корня проекта, только в новый каталог:

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -B \
  diagnostics/plan_ml_selector_contract.py --out /private/tmp/selector-contract-new
```

Создаются plan/CSV/JSONL/manifest, не workers. Готового численного runner для
нового timer/label-контракта пока нет; старый `joint_grid100.py run` его не
заменяет. Следующая реализация должна прочитать эти спецификации, выполнить
mock-validation и получить отдельное разрешение запуска. В этой задаче работа
останавливается после проверки документов, без новых численных результатов.
