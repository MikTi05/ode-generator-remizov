## 1. Предмет сравнения

Канонический набор: `data/all_methods_v1_1000_2026-10-18/`, all_methods_v1,
1000 уравнений / 200 семейств по 5; train/validation/test = 700/150/150,
семейств 140/30/30. Хеши четырёх артефактов и исходников закреплены в
[sources_sha256.json](sources_sha256.json) и `plan.dataset_sha256`.
Основание: [аудит](../ml_selector_readiness/AUDIT_REPORT.md), его JSON и все
1000 CSV-строк прочитаны и проверены. Малый `data/generated/` — другой набор:
совпадение ID без expression_hash недопустимо.

Оба solver решают ограниченную резольвенту на всей ℝ:

\[
L=a\partial_x^2+b\partial_x+c_R, \quad
(\lambda-L)y=g_R, \qquad c=c_R-\lambda, \quad g_R=-g.
\]

В `chernov_solver.py::_apply` используются c_R и положительный дрейф;
`mc_solver.py::_path_contributions` и Numba-код используют
dX=b(X)dt+sqrt(2a(X))dW и потенциал c_R−lambda. Это аппроксимации одного
объекта. Произвольный IVP или задача с произвольными граничными условиями
в контракт не входят. Exact all_methods_v1 имеет компактный носитель,
g=ay″+by′+cy, y0/v0 согласованы с ним; поэтому IVP-представление совпадает.

Обязательны глобальные аналитические сертификаты
0<a_lower≤a≤a_upper, |b|≤B, |c_R|≤C, lambda>C и гладкая конструкция AST.
Проверки на сетке — проверки реализации, не доказательство условий на ℝ.
Для общего горизонта нужен аналитический G≥sup|g_R| из
`all_methods_bounds.certify_all_methods_forcing`.

## 2. Результат и точность

Фиксированы x_j=−1+j/16, j=0, …,32, интервал [-1,1], абсолютный порог eps=.01:

\[
E_{grid}=\max_{0\le j\le32}|f_j-y_{exact}(x_j)|, \qquad E_{grid}\le.01.
\]

Равенство порогу допускается. Никакой перенормировки на амплитуду.
Это сеточная ошибка, не доказанная непрерывная L∞-норма. Один exact из
канонического безопасного AST-загрузчика; численный worker не получает exact
для настройки. Evaluator обращается к exact только после остановки таймера.

Численный ответ допускается к оценке, если success=True, failure_reason пуст,
identity/config/implementation SHA совпадают, x совпадает с target_x, len(f)=33,
все f конечны и результат атомарно сохранён. Для MC проверяются M, все
completed_paths=M, dt_actual, T, RNG/seed и счётчики работы. У R — фактические
n, Q, рабочая сетка и схема. Метрики независимо пересчитываются из f/exact.
success сам по себе не означает достижения .01.

Для новых профилей общий T = `mc_solver.auto_T(lambda, C, G,1e-4)`, вычисленный
одним и тем же правилом; в R передаётся явный T, MC использует ту же auto_T.
Контрольный T берётся из сохранённого production preflight, а будущий worker
заново проверяет вывод G/T. Это контролирует непрерывный хвост, но не весь
ошибочный остаток дискретной схемы. Legacy T taper не смешивается с этим T.

## 3. Статусы и доказательства выполнения

| execution_status | Численный смысл | accuracy_status |
|---|---|---|
| not_run | Нет request/ответа; не запускался | missing |
| interrupted | Запрос есть, целостного результата нет; resume pending | unknown |
| worker_exception / solver_failure | Не получен допустимый f | unknown_error |
| timeout / memory_limit | Ресурсная остановка; время цензурировано | unknown_error |
| invalid_identity / invalid_result | Артефакт не соответствует задаче/контракту | invalid |
| completed | Допустимый конечный ответ | observed_pass или observed_fail по E_grid |

Ошибки вычисления не заменяются E=0, E=∞ или математической неприменимостью.
NaN/Inf не превращаются в конечный успех. При отказе отсутствующая ошибка —
null. История попыток сохраняется, статус итогового профиля не затирает её.
Для операционной вероятности «выдать точный ответ в бюджете» исполненный
failure считается Y=0; это отдельный показатель, не значение E_grid.

## 4. Основная стоимость

Главная стоимость — **warm_end_to_end_method_wall**, `perf_counter_ns`.
Общая безопасная загрузка исходного уравнения/импорт Python до выбора метода
учитывается отдельно. Таймер конкретного метода включает всю необходимую
подготовку G/T, factory/AST, создание solver/config, RNG и вычисление 33 значений.

Будущий wrapper R: start → certify G → auto_T → ChernovSolver.solve → stop.
Wrapper MC: start → prepare_all_methods_mc (включая G) →
solve_monte_carlo_optimized (auto_T) → stop. Не добавлять вторую проверку G
внутри таймера MC, если factory её уже выполнила. Предварительная таблица G/T
служит для preflight/identity, не делает нужную выбранному методу подготовку
«бесплатной». Финальный identity/scoring/SHA I/O после stop, отдельно.

Numba компилируется и прогревается до серии; время import/JIT записывается
отдельно один раз на worker. Не симулировать бесплатный холодный запуск:
`cold_first_call_wall` при необходимости отдельный дополнительный эксперимент.
Прежние `result.runtime_seconds` MC исключают внешний AST/G, поэтому они
не являются новой главной стоимостью. `task_wall_seconds` старых workers
может включать exact scoring и также не подходит без переизмерения.

Одновременно один compute worker, один BLAS/Numba поток, fastmath=False;
никаких параллельных solver или обучения. Зафиксировать hardware/OS/Python,
пакеты/lockfiles, power mode, thermal state, threads и SHA; серии на другой
машине — другой timing cohort. Порядок R/MC чередовать по стабильному хешу
ID+episode. Перед замерами — готовность worker и JIT; охлаждение/паузы вне таймера.

Для финального профиля **4 полных вызова каждого метода на каждом ID**.
MC seeds независимы, все времена включаются независимо от точности;
R должен воспроизводить f. Главная оценка — медиана четырёх времён,
дополнительно min/max, IQR, MAD, все сырые значения. Минимум одного вызова
не используется как устойчивое время. Четыре времени должны быть конечными,
нецензурированными и относиться к одному timing cohort. Иначе timing_unknown.
MAD/median>.20 → timing_unstable и unknown для сравнения двух точных методов;
дополнительные повторы не добавляются после просмотра test.

Если оба метода допустимы: первый быстрее практически, только если
t_fast≤.90*t_slow **и** max(times_fast)<min(times_slow). Иначе при стабильных
временах — practical_tie; заранее заданный выбор Remizov, tie=True. Это
операционная политика с запасом 10%, не тест статистической значимости.
У sole-accurate метода нет необходимости сравнивать время с неточным.

## 5. Два разных target

### observed_fastest_v1 — рекомендованный основной этап A

Конкретный **episode=0** заранее назначен accuracy-ответом каждого профиля.
Для R после четырёх повторов проверяется одинаковость f; для MC ещё три seed
дают отдельные диагностические ошибки/вероятности, не меняя episode0.
Устойчивую стоимость профиля оценивает медиана всех четырёх вызовов, включая
неточные ответы. Не выбирать удачный seed и не усреднять f задним числом.

Таким образом метка описывает наблюдённый ответ episode0 и типичную измеренную
стоимость фиксированного профиля, **не обещает точность нового MC-запуска**.
Дополнительные `observed_fastest_episode1..3` сохраняются как зависимые по
уравнению наблюдения, целиком в том же split. Основная оценка не выбирается
по наиболее удобному episode. Oracle подчиняется тому же правилу.

### reliable_fastest_v1 — отдельный, пока не активированный этап

Кандидат: p_i=P(полный новый вызов выдаёт конечный f с E_grid≤.01 в бюджете)≥.95.
При r заранее фиксированных независимых вызовах Y∈{0,1} считать k/r и точный
Clopper–Pearson интервал. Незапущенные/прерванные оператором запросы не Bernoulli
исходы и не входят в знаменатель; solver/resource failure в фиксированном
бюджете входит как операционный Y=0 и остаётся отдельным статусом.

Для односторонней нижней границы L=BetaQuantile(alpha; k, r−k+1) (L=0 при k=0),
верхней U=BetaQuantile(1−alpha; k+1, r−k) (U=1 при k=r).
L≥.95 → reliability_supported; U<.95 → reliability_rejected; иначе uncertain.
Для двух одновременных сторон делить alpha пополам. Испытания pilot не
объединять с финальными; никакого повторного optional stopping обычных CP-CI.

При 95% доверии без поправки необходимо минимум **59/59 успехов**; для
односторонних одновременных выводов по 1000 задачам Bonferroni — **194/194**,
для двух сторон — **207/207**. С отказами минимальный r ещё больше.
Формула для всех успехов: L=alpha^(1/r). Четыре повтора финального observed
benchmark надёжность .95 не подтверждают. Агрегат из четырёх seeds, если будет
выбран отдельным алгоритмом, требует **59 независимых агрегатов**, не 59 путей
и не разбиения одного агрегата на 4 Bernoulli-наблюдения.

Bernoulli проверяется по **полной наблюдённой E_grid**, поэтому включает шум,
фиксированное h-смещение и усечение. Для такого эмпирического p-утверждения
не требуется отдельная аналитическая граница h-смещения. Однако pointwise CI
дискретного среднего из MCResult или CI среднего f не заменяют эту проверку.
Для переноса на другие h/T/M/задачи данное p-утверждение не действует.

## 6. Таблица меток и неопределённость

Для выбранного target eligibility ∈ {pass, fail, unknown}. Для observed это
E_grid episode0 при completed; для reliable — подтверждённая/отвергнутая
надёжность (R — воспроизводимый детерминированный grid-результат).

| R eligibility | MC eligibility | Метка |
|---|---|---|
| pass | fail | remizov |
| fail | pass | monte_carlo |
| pass | pass | сравнение медианных времён; practical tie → remizov+tie |
| fail | fail | none, строго среди этих профилей/бюджетов |
| любое | unknown | unknown, в том числе R pass + отсутствующий MC |
| unknown | любое | unknown |

Если timing неизвестен у двух pass, метка unknown. Ошибки исполнения дают
unknown в observed numerical labels; отдельно допустима operational-policy
оценка с delivery failure. Не заменять неизвестность прогнозом старой ML.
`none` не утверждает математическую недостижимость .01 или отсутствие иных
конфигураций. Для трека B неизвестная клетка, способная изменить минимум,
делает минимум/метку unknown, а не игнорируется.

На каждую строку сохранять dataset SHA, ID, expression_hash, family/split,
profile/version, full config, timing cohort, execution/accuracy/reliability
statuses, четыре f/exact/error/time/seeds, CI/r/k, label_type/version,
chosen_method, tie, reason, admissible set и missing configurations.
ML-входы и targets физически разделены.

## 7. Управление версиями и условия остановки

Численная/статистическая политика выбирается только на train. Validation —
выбор ML; test — единая итоговая оценка после фиксации профилей и модели.
Уже известная история test делает его историческим holdout, не новым pristine
prospective test. Свежие MC seeds независимы; для независимости от всей истории
исследования нужен отдельный новый семейный test в будущей задаче.

Не менять параметры по test, не добирать seed после CI, не объединять разные
профили. Изменение контракта — новая версия и новый пререгистрированный план.
Safety stop, неверный SHA, invalid identity или budget stop останавливают серию
с сохранением completed/pending. Resume повторяет только незавершённый ключ
с новым attempt ID, сохраняя семантический seed; старый результат неизменяем.

Рекомендация: начать с A/observed_fastest, публиковать p-CI как неопределённость.
Выбор .95 как обязательного reliable-критерия и соответствующий большой бюджет
требуют отдельного решения пользователя; в plan это **false**. Сейчас ни один
документ не разрешает запуск. Связанные документы:
[профили](PROFILE_MATRIX.md), [пилот](MC_PILOT_PLAN.md),
[benchmark](BENCHMARK_PLAN.md), [ML](ML_SELECTOR_SPEC.md), [решения](DECISIONS.md).
