# Завершение benchmark1000 после train-пилота

Статус: **план, не запущен**. Рекомендуется A/observed_fastest; reliable и B
не являются скрытыми дополнительными требованиями. Переходы ниже конечны,
не зависят от желания получить победы MC. [Контракт](CONTRACT.md) обязателен.

## 1. Входной реестр и точная недостача

[benchmark_requirements.csv](benchmark_requirements.csv) содержит все 1000 ID,
expression_hash, split, совместимость численных массивов и необходимость timing.

| Профиль | Совместимые численные задачи сейчас | Отсутствуют | Финальные однородные 4-call timing блоки |
|---|---:|---:|---:|
| R128 zero/commonT | 100 | 900 | 0/1000 |
| R256 zero/commonT | 5 | 995 | 0/1000 |
| MC0 single1024 grid33 | 100 primary | 900 | 0/1000 по новому timer/seed schedule |
| MC1 single4096 grid33 | 5 с 4 seed | 995 | 0/1000 |
| MC2 single4096, h1/256 | 0 | 1000 | 0/1000 |

Исторические taper997/3 — отдельный профиль, не замена R128zero.
Массовые MCx0 и старые малые данные не заполняют grid33-клетки.
После будущего пилота пересчитать реестр; не считать его planned jobs фактами.
Проверять эффективный T, grid, source SHA, все численные параметры, backend, RNG,
а не только «похожий» profile name. Для R возможна нормализация config T=None
к реально вычисленному T только при проверенном совпадении правила/значения.

**Почему всё же нужны новые вызовы даже при сохранённом f:** численные массивы
можно использовать для accuracy-проверки/детерминированного replay, но старые
времена не включают одинаковый preprocessing и не дают 4 повторов в одном cohort.
Для честных per-equation fastest-labels нельзя восстановить эти времена из f
или прогнозов ML. Новые timing-вызовы одновременно дают окончательные f,
поэтому отдельно пересчитывать 1000 задач «для ошибки» до timing не требуется.

## 2. Последовательность работ

1. Принять основной track A/observed или более дорогой reliable, принять
   ресурсы первого этапа пилота. В отдельной задаче реализовать worker и
   record schema по контракту, не меняя схемы solver. Проверить таймер, hash,
   exact-isolation, conditional queue, resume и budget на mocks.
2. Выполнить R0+P1, затем только разрешённую ветку P2 из MC_PILOT_PLAN.
   При всех MC0 успехов остановить автоматическое расширение и решить,
   полезен ли полный отрицательный контроль. Не подменять результат иной целью.
3. Заморозить два профиля, labels/ties, cost schema, seed schedule, code/environment,
   список допустимых конфигураций и бюджет. Создать immutable
   `frozen_profiles.json`, полный `jobs.jsonl`, manifest SHA и plan hash.
4. Production order: train700 → validation150 → test150. Train позволяет
   оценить и уточнить **цену исполнения**, но численные параметры выбранных
   профилей уже фиксированы. При изменении профиля предыдущая версия
   завершается отдельным результатом; нельзя незаметно менять его на части 1000.
5. Замеры вести партиями по 20 **уравнений**, внутри 4R+4MC на каждый ID,
   последовательно. После первых 20 train сверить фактическую цену,
   thermal/RSS/частоту failures с выделенным бюджетом и обновить forecast.
   Если стоимость неприемлема — budget stop с partial registry, без ложного
   «полного benchmark». Не расширять ресурсы автоматически.
6. Сохранить predictions/models/thresholds после train/validation ML и только
   затем открыть итоговые test-labels evaluator. Test-солверные ответы могут
   храниться запечатанно; код анализа профилей не должен читать их до freeze.
   Если обучать ML ещё рано, выполнить test после фиксации протокола и хранить
   метрики как исторические; для строгой будущей независимой оценки ML
   понадобится новый holdout. Предпочтительнее отложить test-отчёт до ML-freeze.

На всех этапах можно остановиться по выделенному бюджету, но не по отсутствию
нужного класса побед. План завершения 1000 не обещает ни полного accuracy-
покрытия, ни MC-конкурентности. Его завершение означает, что каждая обязательная
задача/профиль исполнена либо имеет явно зафиксированный terminal failure.

## 3. Финальные повторы и seeds

По 4 вызова R и MC на ID, одинаковая 33-точечная цель и timer. Для MC выбранный
profile использует четыре **новых** seed из `plan.final_seed_schedule`;
они не пересекаются с pilot или прежними сериями. Episode0 заранее основной,
episodes1..3 — диагностические и дополнительные наблюдаемые labels.
R —4 детерминированных повторения, без выбора лучшего времени.

Порядок method внутри episode чередовать по SHA256(ID|episode), не запускать
два compute процесса. Загрузка общая вне таймера; method-specific G/T/AST внутри.
Exact/scoring и JSON/SHA после stop. Изменение chunk, backend, компилятора,
threads, hardware или численного кода создаёт новый profile/cohort.
Бюджет watchdog пер-задачу из train-профильного preflight; test не используется
для настройки h/M/n. Превышение watchdog сохраняется как цензурирование.

## 4. Хранение, resume и отказ

Новый путь `results/selector_benchmark_v1_<date>_<runid>/`, exist_ok=False.
Структура: frozen plan/source snapshot; jobs; requests; attempts; immutable results;
events; telemetry; sessions; environment; analysis. Semantic key:
dataset_hash/equation_id/expression_hash/profile_hash/cohort/episode.
Attempt ID дополнительный, не заменяет semantic key.

Перед request проверить старый terminal по полному ключу и SHA. Если completed
и совместим — не повторять этот ключ. Публикация — atomic temp+fsync+rename
без перезаписи; результат содержит raw f, config, seed, RNG, статус, wall/RSS/work,
timestamps и ошибки evaluator. На исключении сохранять traceback/returncode/
signal вместо прежней недостаточной диагностики трёх R-worker-exit.

Прерванный request без complete result остаётся pending, его новая попытка
имеет тот же seed и новый attempt ID; вычислительная работа обеих попыток
сохраняется, для оценки берётся одна полная реплика. Это не независимый seed.
Terminal solver/resource failures не повторяются автоматически. Для численного
accuracy-target f отсутствует; в операционном delivery отчёте failure остаётся
неуспешным исполнением. Все counts имеют раздельные знаменатели.

Guardian/RSS/lease по проверенному `diagnostics/chernov_batch_control.py`,
пример batch/worker в `diagnostics/joint_grid100.py`. Прямой запуск этого старого
CLI не исполняет новый контракт: у него другой timer, seed schedule и schema.
Общий compute cap и per-attempt watchdog задаются до запуска; не подменять
их количеством итераций. Hard-stop хранит elapsed и неизвестные partial counters.

## 5. Ресурсы: что подтверждено и что лишь сценарий

Подтверждённые старые measurements: joint100 R primary1238.33 solver-с,
MC primary1833.88 solver-с; final5 R256117.78 solver-с и 20MC4096505.03 solver-с.
Источники — соответствующие `analysis/summary.json` и raw.

[benchmark_cost_scenarios.csv](benchmark_cost_scenarios.csv) содержит сценарии
для каждого кандидата: прямой MC0 grid100, для остальных задач mean4x0×33,
затем масштаб по path_updates; для R — среднее joint100 с масштабом n.
Это не измеренное будущее время, не верхняя граница и не оценка стоимости
«достичь .01». Preprocessing/JIT/паузы и изменение производительности исключены.

Основной A требует **4000 R +4000 MC =8000 новых timing calls** на 1000 задачах.
Самая дешёвая пара R128+MC0 — сценарий примерно суммы столбца 4-call CSV;
более дорогие MC1/MC2 могут требовать существенно большего выделенного времени.
Итоговые числа приведены в DECISIONS и JSON/CSV; до запуска их заменить
preflight по фактическому P1/P2 end-to-end wall. Ни историческая 60-секундная
отсечка, ни старый 14.4 к-секундный cap не переносятся как универсальные.

Если budget не покрывает 1000×4×2, варианты честного результата:
поэтапное выполнение с resume; ограниченный измеренный поднабор и partial
coverage; более узкий quality-проект R. Нельзя присвоить недостающим 900 MC none,
использовать предсказанные времена вместо measurements или объявить
общую полную эффективность по одному x0.

Для reliable критерия 59 успешных вызовов на каждом ID даже в идеальном случае
нужно 59000 MC-вызовов против 4000 observed; совместное 194 —194000. Все failures
увеличивают нужный r или приводят к unknown/rejected, не дают бесплатного
certificate. Этот вариант сейчас не предлагается как обязательный.

## 6. Вариант B: минимальное измеренное время

После A, при отдельном бюджете, объявить Θ_R и Θ_MC и заполнить дополнительные
клетки. Для полного множества R128/R256+MC0/1/2 всего 20000 вызовов
(5 профилей×1000×4), из которых 8000 относятся к A при совместимом timer/cohort.
Потребуется ещё 12000; если hardware изменился, старое timing не смешивать.
Для каждой конфигурации eligibility и median time отдельны; минимум по реально
измеренным admissible конфигурациям. Не минимизировать по seed.

Если цель — время автоматического достижения допуска онлайн, то дополнительно
нужна реализованная **без exact** политика настройки и цена всех её попыток.
Текущий T* — офлайн measured oracle, не такой адаптивный алгоритм. Не списывать
цену train-поиска или runtime-search как бесплатную часть развёртываемой политики.

## 7. Проверка перед ML и независимость

Пересчитать f/exact/grid/error каждого completed ответа, идентичность и finite;
сверить конфигурации, full keys, counts, завершённость guardian и отсутствие lock.
Отдельные таблицы по всем 1000 и split, флаги label type/tie/unknown/coverage.
Для обучения observed-model нужен выбранный профиль, численные targets на train,
сопоставимые времена, достаточные classes и удержанный validation. Для окончательной
оценки — зафиксированная модель до раскрытия test, равные budgets baseline/oracle.

Исходный test ранее изучался численно. Новые seed обеспечивают независимость
MC-реплик, а train-only решения нового контракта ограничивают дополнительную
утечку; это не стирает историю. Для независимости от всех прежних исследовательских
решений требуется новый датасет семейств с отдельными seed/версией/эмбарго,
что в текущее задание не входит и не генерировалось.
