## Вопросы и предел вывода

Может ли существующий Numba MC на 33 точках дать E_grid≤.01 при M1024→4096
и h1/128→1/256; сколько стоит вызов; устраняет ли шаг часть остатка?
Пилот ищет практически измеримый профиль, не доказывает p≥.95, не требует
MC-побед и не оценивает популяционную частоту успеха обогащённой выборкой.
Нельзя увеличивать M/h-бюджет за её пределы после неудачи.

## Параметры, seeds и агрегация

MC0:M1024, h1/128; MC1:M4096, h1/128; MC2:M4096, h1/256.
Все — Numba,33 точки, chunk1024, block64, аналитический общий T/tail1e-4.
Никакой табуляции коэффициентов, h512 или скрытого coupling.
Сравнение MC0→1 меняет только M; MC1→2 — только h.
Между профилями seed независимы; парный coupled тест не заявляется.

На каждую испытываемую пару ID/profile **4 независимых полных вызова**.
Seed(stage, profile_index, episode)=248800000000+stage*10000+profile_index*100+episode,
episode0..3. Stage1:248800010000–003 для MC0,010100–103 для MC1,
010200–203 для MC2 (числа целиком — в JSONL). Stage2 использует stage=2,
финальный benchmark stage=3. Существующий point_address_v1 добавляет ID/x;
использование общего base seed для разных уравнений не повторяет их потоки.
Проверена непересекаемость с прежними production seeds.

Основной ответ — каждый отдельный вызов, ошибки и времена всех 4 сохраняются.
Mean4 допустим только как вторичный diagnostic с отдельным ID/стоимостью;
он не заменяет single labels и не образует 4 повторов агрегированного алгоритма.
Старые final5 outputs — диагностическая база, не свежие повторы текущего плана.

## Этапы и правила перехода

**P0, только чтение:** сверить dataset/expression/source SHA, целостность raw,
profile/T, эффективный h, полноту повторов, дисковый запас и environment.
Сейчас выполнены идентификация и статический preflight по сохранённым файлам.
Диск, активное окружение и аппаратное состояние проверяются перед будущим
запуском. Проверка worker и его timer требует реализации и dry-run с mocks.

**R0, train-выбор n:** из 40 уже есть 37 совместимых R128 и 5 R256.
Нужно 3 новых R128 и 35 новых R256, итого **38** численных клеток.
Сохранённые массивы не пересчитываются для этой проверки точности.
Выбор R по правилу PROFILE_MATRIX; время старых ответов только ориентир.
Эти 38 — не повтор трёх taper-failure, а zero/commonT-клетки.

**P1, пять sentinel:** 5×3 MC-профиля×4 seed = **60** новых вызовов.
Порядок — детерминированные блоки equation/episode; профили чередовать
циклически по SHA, чтобы дорогой профиль не всегда шёл последним.
До всех 4 повторов профиля на 5 задачах не принимать accuracy-futility решение.
Resource/SHA/guardian stop может остановить раньше с pending, не с отрицательной
математической меткой. Перезапуск не расширяет общий выделенный бюджет.

На закрытом P1 посчитать для каждого кандидата:
s из 20 completed точных full-grid ответов; число failure отдельно;
медиану времени конечных нецензурированных вызовов и медиану E конечных
ответов, обязательно с числом доступных значений из20; по каждой задаче k/4
и двусторонний 95% CP-CI. Эти CI описательные/индивидуальные, не совместная
сертификация 40 задач. Если отказов, точные ошибки отсутствующих не подставлять.

Предварительно заданные train-gates:

1. Профиль с >1 operational failures из 20 не проходит в массовую ветку.
   Guardian/операторская остановка — incomplete P1, нельзя применять этот порог.
2. Для MC1/MC2 median20 warm cost должен быть ≤8×median20 MC0.
   Порог 8 — предлагаемое ресурсное ограничение, не закон сходимости.
3. Дорогой профиль с s=0 и medianE≥.8×medianE_MC0 прекращает исследоваться.
   Это эвристика бесперспективности по заранее ограниченному бюджету;
   не доказательство p=0 или неприменимости MC. Если medianE из-за отказов
   не определена, флаг unknown, не положительное решение гейта.
4. Среди оставшихся: максимум s, затем устойчивое время; разница<10% —
   фиксированный приоритет MC0, MC1, MC2. Счёт побед над R не используется.
5. Если все s=0, **не запускать P2 автоматически**. Зафиксировать нулевую
   наблюдаемую точность и выбрать отдельным решением: закончить исследование
   этих бюджетов или провести полный отрицательный контроль MC0. Это не
   подмена научной задачи и не требование получить класс MC-winner.

**P2, оставшиеся 35:** только один выбранный MC-профиль, по 4 новых seed,
максимум **140** вызовов. Другие два из 420 условных JSONL строк запрещены.
Всего по активной ветке максимум **200 новых MC-вызовов +38 R**, а не 518.
По P2 можно принять выбранный профиль для фиксированного сравнения или
отклонить его по неполноте/бюджету; нельзя перебрать альтернативы на этих же
35 задачах без новой версии плана. Нулевая доля MC-побед не критерий отказа.
Все 40 — train; P2 — проверка переносимости с sentinel, не внешний holdout.

**Freeze:** сохранить выбранные R/MC profile IDs, параметры, исходники, решение
по A/reliable, стоимость и полные правила labels. До freeze ни validation,
ни test не используются для настройки численных параметров.

## Стоимость и ресурсы

По [cost_forecast.csv](cost_forecast.csv) P1: **1667.13 с** solver-сценария;
R0: **901.16 с**; вместе **2568.29 с /42.80 мин** без внешней подготовки.
Предлагаемый выделенный compute cap для R0+P1 = ceil(2×сценарий+300) =
**5437 с /90.62 мин**, один worker512MiB. Это предложение для будущего запуска,
не универсальный лимит проекта и не разрешение потратить это время сейчас.

Если выбран MC2, максимальная ветка MC P1+P2 по operation-scaled сценарию —
**20272.21 с /5.63 ч**, плюс R0; более дешёвые ветки видны в CSV.
Поэтому «40 задач» нельзя автоматически назвать коротким расчётом.
Для P2 отдельный compute cap замораживается после P1 по формуле
ceil(2×сумма прогнозов оставшихся вызовов+300), с заменой коэффициента
стоимости на измеренный end-to-end P1; продолжение требует принятия бюджета.

Основание: прямой сохранённый MC0 grid33 wall на той же задаче; где его нет —
median4 x0 wall×33. Новый M/h масштабируется по отношению точных path_updates.
Это **сценарии**, не измеренные длительности новых профилей, не доверительные
интервалы и не верхние границы. Накладные расходы AST/G и изменение throughput
на мелком h не измерены. После первых закрытых блоков P1 проверить прогноз;
не увеличивать cap автоматически. Новых вычислений ради оценки цены нет.

Per-attempt watchdog в JSONL: ceil(max(120,6×scenario_seconds+15)); MC
max_path_steps=33*M*N, не default1e8. Предлагаемый 512MiB сопоставим с
прежними наблюдениями около 282–286MiB, но не гарантия. Guardian, lease300 с,
RSS sampling .25 с и job-level telemetry по образцу `joint_grid100.py`.
Остановки не записывать как finite inaccurate; raw/partial work и wall сохранять.
При stalls/thermal stop не пересчитывать completed ответы.
