# Отдельный backend Monte Carlo с точной AST

Исходный `mc_solver.py` остаётся эталоном. `mc_optimized.py` использует прежние
`RemizovProblem`, `MCConfig`, аналитический сертификат G и общий контракт
`MCResult`, добавляя измерения подготовки, JIT, RNG и физической работы AST.

```bash
.venv/bin/python -m pip install -r requirements-mc-optimized.txt
```

```python
import numpy as np
from all_methods_dataset_loader import load_all_methods_equations
from mc_solver import MCConfig
from mc_optimized import prepare_all_methods_mc, solve_monte_carlo_optimized

equations = load_all_methods_equations(
    "data/generated/all_methods_equations_v1.csv",
    "data/generated/all_methods_equations_v1_metadata.jsonl",
)
prepared = prepare_all_methods_mc(equations[0].metadata)
result = solve_monte_carlo_optimized(
    prepared, np.array([0.]),
    MCConfig(M=1024, chunk=1024, dt=1/128, T=None, seed=20261025),
    engine="numba", block_steps=64,
)
```

Это пример вызова, а не установленный профиль достижения полной ошибки .01.
Для 33 точек явно проверять `max_path_steps` по N×M×33: штатный лимит
100 млн может быть недостаточен. Повышать бюджет осознанно до запуска.

`prepare_all_methods_mc` принимает валидированную конструкцию all_methods_v1,
заново проверяет whitelist AST, коэффициенты и глобальные сертификаты,
восстанавливает `RemizovProblem`. Metadata здесь является определением
функций; произвольные callbacks не заменяются без проверки. Для других
уравнений остаётся исходный solver; отдельно доступны два явных аналитических
fixture `prepare_analytic_mc('constant'|'gaussian')`. Не создавать вручную и
не изменять `PreparedMC`/его массивы: compiled kernels доверяют фабрике.

Четыре дерева переводятся в постфиксные массивы opcode/индексов/коэффициентов.
Для a,b,c_R нужны только значения; аналитические производные y_shape нужны
для заданной правой части и остаются. В каждой новой точке траектории a,b,c_R,g_R
вычисляются совместно, a,b используются на следующем шаге. Это сохраняет
коэффициенты исходного ОДУ на всей R; пространственной таблицы нет.
Строки формул не исполняются через eval/exec.

`engine='numpy'` использует value-only коэффициенты и прежний jet решения;
Numba ему не нужен. `engine='numba'` использует последовательный nopython
интерпретатор AST и цикл Эйлера–Маруямы; `fastmath=False`, без параллельных
редукций. Обе трапеции и порядок суммирования вкладов сохранены. Обобщённые
сигнатуры компилируются один раз на процесс, без отдельной компиляции каждого
уравнения и без дискового cache. Время первого импорта/JIT входит в runtime
решателя и runtime-budget, подготовка AST снаружи отражается отдельным полем.
`compile_backend()` позволяет заранее измерить эти расходы без решения ОДУ.

PCG64/SeedSequence и адреса точек те же, что в эталоне; один вызов
`standard_normal(m)` на шаг, в прежнем порядке. Блок по умолчанию содержит
64×m нормалей (при m=1024 — 0.5 МиБ). Размер блока не меняет успешный ответ,
chunk остаётся частью RNG-конфигурации. Отмена проверяется между блоками,
поэтому deadline может быть превышен на один блок. Дорогие серии требуют
внешнего guardian, как в диагностическом драйвере.

На отказе результат пуст, завершённые полные chunks учитываются отдельно.
`n_normal_draws` содержит реально сгенерированные значения, включая отброшенный
остаток блока. `n_path_steps` считает выполненные обновления, в том числе
часть отклонённого блока; `fused_point_evaluations` — физические вычисления.
`coefficient_calls/values` — совместимые логические количества ролей эталона
для завершённых chunks; это не число физических callback-вызовов backend.
Первые/последние проверки коэффициентов могут находиться в другом месте
блока; работа до отказа и причина при одновременно нескольких нарушениях
не обязаны побитово совпадать с эталоном. Проверки конечности значений AST,
необходимых jets, состояния и статистики, a>0 и глобальных bounds сохранены.
Неиспользуемые производные коэффициентов больше не вычисляются и не проверяются.

Между NumPy ufunc и scalar libm возможны различия округления. Обязательная
регрессия сравнивает коэффициенты, jets, отдельные траекторные вклады, средние
и stderr на одинаковых нормальных входах; побитовая идентичность между
платформами не обещается. Глобальный G контролирует только непрерывный хвост.
Статистические интервалы относятся к дискретному усечённому среднему;
временное смещение и полная точность этим backend не сертифицируются.

Замеры и протокол: `results/mc_optimized_backend_2026-10-25/REPORT.md`.
Драйвер `diagnostics/benchmark_mc_optimized.py`: `freeze`, затем `run` в новом
каталоге с protocol.json; независимый guardian, один worker, ограниченная
память, owner lease. Владелец продлевает lease через
`diagnostics.chernov_batch_control.renew_owner`, остановка — `request_stop`.
Повторный запуск в тот же каталог запрещён файловым контрактом.
