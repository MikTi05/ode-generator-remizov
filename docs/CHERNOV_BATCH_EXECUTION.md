# Безопасный пакетный запуск Chern

Работать из корня проекта, использовать `.venv`. Математическая схема не менялась:
`ChernovSolver.solve`, n=128, 513 узлов, dx=0.0125, padding=12, cubic+taper,
tail_eps=1e-8, n_jobs=1, проверка ошибки на 33 точках [-1,1].

**Текущий результат, 2026-10-18:** серия завершена, pending=0. Сохранены все
1000 итогов: 997 конечных ответов, 871 с E∞≤0.01, 126 выше порога,
3 прежних worker_exception. Последние 300 решены за 15 автоматических партий
по 20; новых вычислительных отказов нет. Все процессы завершились, блокировки
свободны. [Отчёт и полный CSV](../results/chernov_managed_completion_2026-10-18/final/REPORT.md).

## Ограничение процессов и владение запуском

Одновременно разрешён **один вычислительный worker во всём проекте**, даже если
старый план содержит `workers=8`. Глобальные блокировки контроллера и вычислительного
слота дополняют блокировку конкретного каталога. `n_jobs!=1` отклоняется; прямой
вызов внутреннего worker без guardian отклоняется.

Помимо worker существуют контроллер и отдельный малонагруженный guardian.
Guardian работает в своей POSIX-сессии, а worker с потомками — в отдельной группе.
При остановке guardian посылает группе SIGTERM, затем при необходимости SIGKILL,
и ожидает worker. Не используются широкие команды `pkill python` или PID из
старых файлов для уничтожения произвольных процессов.

Guardian независимо от потока worker наблюдает за:

- EOF управляющей трубы: аварийная смерть контроллера, включая SIGKILL;
- heartbeat контроллера: отсутствие более 5 с, в том числе SIGSTOP/зависание;
- командой остановки в каталоге текущей сессии;
- внешним разрешением владельца: срок **120 с с последнего продления**.

Контроллер сам не продлевает внешнее разрешение. Остановка Codex или закрытие
редактора не всегда завершает ОС-процесс контроллера; без внешнего продления
guardian всё равно остановит вычисление примерно за две минуты плюс завершение
группы. Сигналы SIGINT/SIGTERM/SIGHUP и `--stop` инициируют немедленную остановку.
Защитные блокировки удерживаются до завершения очистки. Worker наследует FD
вычислительной блокировки: даже смерть guardian не открывает второй слот,
пока первый worker ещё существует; внутренний контроль родителя остаётся
дополнительной защитой. Ошибка очистки явно записывается, не выдаётся за успех.

## Команды для существующей серии

Каталог результатов:

```bash
batch_results=results/chernov_solve1000_2026-10-18
```

Посмотреть сохранённые результаты и состояние блокировок, без вычислений:

```bash
.venv/bin/python -B diagnostics/run_chernov_batch.py --output-dir "$batch_results" --status
```

Остановить из другого терминала:

```bash
.venv/bin/python -B diagnostics/run_chernov_batch.py --output-dir "$batch_results" --stop
```

Также можно нажать Ctrl+C в терминале контроллера. Незавершённая задача останется
pending; уже опубликованный результат сохраняется. Команда `--stop` ждёт
подтверждения guardian; при неудачной очистке сообщает это явно. Историческое
`active.json` после SIGKILL может остаться с `finished=false`: смотрите также
guardian и фактические блокировки в `--status`.

## Длительный управляемый запуск всех pending

2026-10-18 пользователь разрешил завершить остаток без ручного запуска каждой
партии. На момент этого решения сохранено 700 терминальных записей, pending=300.
Режим явно включается `--all-pending`; по умолчанию сохраняется прежняя малая
партия без автоматического продления разрешения.

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -B diagnostics/chernov_monitored_batch.py \
  --output-dir results/chernov_solve1000_2026-10-18 \
  --run --all-pending --batch-size 20 --thermal-state-only
```

Один внешний монитор последовательно запускает партии по 10–20 (default 20;
последняя может быть меньше), между ними выдерживает минимум 60 с без worker.
Блокировка монитора удерживается и во время пауз. Каждый новый backend по-прежнему
может иметь максимум одного worker, n_jobs=1, BLAS=1. После каждого уравнения
ответ публикуется прежним атомарным механизмом. Все терминальные результаты,
включая прежние ошибки и accuracy_not_met, пропускаются.

Guardian сохраняет разрешение **120 с** и контроль трубы/heartbeat backend.
Только внешний монитор в режиме all-pending продлевает lease, раз в 20 с,
после свежего успешного сэмпла thermalState/CPU/RSS и проверки совпадения
controller/session/token/worker/guardian. Просроченное разрешение не оживляется.
Сам backend разрешение не продлевает. При SIGKILL/зависании монитора продления
прекращаются: независимый guardian останавливает worker по истечении lease.
При потере backend-контроллера действует прежняя немедленная реакция на EOF
или 5-секундное истечение heartbeat. Монитор также останавливается при потере
собственного родителя. Это управляемое продление, а не отключение lease.

Любая ошибка телеметрии, thermalState выше nominal, лишний worker, неправильное
владение процессом, неудачная очистка или новый вычислительный отказ останавливают
**всю серию**, без автоматического повтора/продолжения после отказа. Конечный
численный ответ с accuracy_not_met сохраняется и не прерывает серию. Пороги
CPU>125% и RSS>512 МиБ, интервал сэмплов 2 с сохранены. Во время пауз тепловое
состояние и отсутствие worker также контролируются. Температура в °C не измеряется.

Остановка всей серии, в том числе во время паузы, — Ctrl+C в терминале монитора
или следующая команда из другого терминала:

```bash
.venv/bin/python -B diagnostics/chernov_monitored_batch.py \
  --output-dir results/chernov_solve1000_2026-10-18 --stop
```

Она ставит token-scoped stop-файл монитора и при активном backend использует
прежнюю команду остановки guardian. Низкоуровневый `run_chernov_batch.py --stop`
останавливает только текущий backend; для остановки во время паузы нужна команда
монитора выше. Повтор команды запуска создаёт новый журнал и продолжает pending;
старые попытки/ответы/журналы остаются. Новая директория содержит series.json,
batch_*/run.json, samples.jsonl, lease_renewals.jsonl, controller.log и журнал
пауз cooling_samples.jsonl. Указатель текущего монитора —
`results/chernov_monitored_active.json`; он не заменяет историю в директории серии.

## Прежний режим одной малой партии с контролем нагрева

Для отдельно ограниченной партии:
Запускать в обычном терминале на переднем плане, наблюдая за выводом и нагревом
ноутбука. Для текущего продолжения использовать оболочку мониторинга:

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -B diagnostics/chernov_monitored_batch.py \
  --output-dir results/chernov_solve1000_2026-10-18 \
  --run --max-new 3 --thermal-state-only
```

Один вызов обрабатывает **не более трёх новых задач**; можно выбрать 1 или 2.
После завершения обязательна пауза **не менее 60 с**: новый вызов до её окончания
будет отклонён без запуска worker. Следующую партию запускает оператор отдельно,
после проверки активности и нагрева. Циклы автоматического запуска всех pending
в этом режиме не предусмотрены. Для всей серии используется явный режим выше.

Каждые 2 с оболочка сохраняет CPU/RSS, число вычислительных worker и macOS
`NSProcessInfo.thermalState`. Она останавливает свою партию при любом состоянии
выше `nominal`, более одном worker, CPU worker >125% (100% соответствует одному
ядру), RSS >512 МиБ или недоступной телеметрии. До запуска также проверяются
телеметрия, блокировки и отсутствие вычислительных worker.

Температура CPU в °C здесь **не измеряется**: macOS thermalState — системный
индикатор, причём неподдерживаемая/неизвестная система также может вернуть
nominal. Пользователь согласовал этот режим вместе с собственным наблюдением
за нагревом. Флаг `--thermal-state-only` явно подтверждает это ограничение;
при заметном нагреве остановить партию через **Ctrl+C** или `--stop` выше,
даже если состояние пока nominal.

В режиме одной малой партии разрешение guardian истекает через **120 с**,
оболочка его **не продлевает** и не перезапускает вычисление после остановки. Если бюджет
закончится раньше партии, уже готовые ответы сохранятся, незавершённая задача
останется pending. Команда внешнего продления существует для отдельного явно
контролируемого запуска, но **не входит в этот протокол малых партий**:

```bash
.venv/bin/python -B diagnostics/run_chernov_batch.py --output-dir "$batch_results" --keep-alive
```

Не автоматизировать продление. Не использовать `--init` для существующего
каталога и не запускать низкоуровневый драйвер без ограничения размера партии.
В режиме малой партии монитор не переходит к следующей партии.

Новые журналы мониторинга автоматически создаются в отдельном
`results/chernov_small_<UTC>_<id>/`: run.json (план, хеши, итоги), samples.jsonl,
controller.log. Общая история пауз — `results/chernov_small_batch_history/`.
Если сам монитор аварийно исчез, пауза консервативно учитывает ещё 120 с lease.
Параметры численной схемы остаются из исходного plan.json; точное решение
используется только при последующей оценке ошибки.

## Сохранение и продолжение

`attempts/<attempt>/result.json` публикуется атомарно после каждого уравнения;
затем `solutions/<ID>.json` и progress. Файлы результатов не перезаписываются.
Если контроллер погиб между публикацией ответа worker и checkpoint, продолжение
подхватит ответ из attempts. Завершённые записи, включая accuracy_not_met и
worker_exception, пропускаются. Оборванный запрос получает новую попытку,
старые запросы/логи остаются. Терминальные отказы автоматически не повторяются.

Исходный plan.json и его SHA-256 сохранены; прежние 694 записи продолжают
проверяться по исходному плану. Новая `safety_policy_v2.json` разрешает только
зафиксированную миграцию управляющего кода, хранит старые/новые SHA-256 и ссылки
на резервные копии. Численные источники и данные должны совпадать с прежними
хешами. Новые сессии и ответы отдельно записывают политику надзора/её хеш.
