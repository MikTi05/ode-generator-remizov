# Две адаптированные схемы Chern

Новый модуль `chernov_solver.py` принимает тот же `RemizovProblem`, что и
исходный решатель. Снимок предоставленного кода и ноутбука сохранён в
`comparison_inputs/`; исходное математическое ядро проекта не изменено.

## Запуск на сохранённом датасете

Из корня проекта:

```bash
.venv/bin/python -B examples/solve_chernov_equation.py \
  --equation-id AMV1_F0005_S00 --scheme solve --n 32 --num-t 257 \
  --dx 0.025 --padding 8

.venv/bin/python -B examples/solve_chernov_equation.py \
  --equation-id AMV1_F0005_S00 --scheme streaming --n-steps 8192 \
  --dx 0.025 --padding 8
```

Обе команды читают CSV/JSONL из `data/generated/`, ничего не записывают и
печатают JSON с результатом, конфигурацией и E∞ относительно `y_exact` на
33 точках [-1,1]. Код выхода: 0 при конечном результате, 1 при штатном отказе.
Успех не означает достижения заданной точности.

Библиотечный интерфейс:

```python
from chernov_solver import ChernovConfig, ChernovSolver

solver = ChernovSolver(equation.remizov_problem,
                      ChernovConfig(n=32, num_t=257, n_steps=8192))
fixed = solver.solve(target_x)
streaming = solver.solve_streaming(target_x)
```

Каждый вызов заново готовит сетку и коэффициенты. `runtime_seconds` включает
эту подготовку и проекцию ответа на target_x, но не загрузку CSV/JSONL,
выполненную до вызова. `preparation_seconds` сохраняется отдельно.

## Постановка и схемы

Решается (λ−L)y=g_R на всей R, L=a∂²+b∂+c_R. Используются именно
`problem.c_remizov` и `problem.g_remizov`, а не обычные c и g задачи Коши.
Начальные условия не являются входом схем.

* `solve`: составной Simpson для exp(−λt) S(t/n)^n g_R; n фиксировано.
  Число `num_t` округляется вверх до нечётного; сетка uniform или quadratic.
* `solve_streaming`: τ=T/K, u_0=g_R, u_k=S(τ)u_(k−1), равномерный Simpson.
  K=`n_steps` округляется вверх до чётного. Поля n, num_t и t_grading здесь
  не определяют расчёт. Это отдельная конечная аппроксимация.

Формула S, веса и знак дрейфа сохранены. Коэффициенты и forcing кэшируются
на одной фиксированной рабочей сетке. Геометрия сдвигов повторно используется
при одном τ. Сплайн перестраивается для каждого нового состояния.

## Отличия адаптации от предоставленного Chern.py

* Глобальные аналитические сертификаты берутся из RemizovProblem; сеточная
  оценка sup|c_R| не используется. Проверки значений используют существующие
  функции remizov_solver, без изменения этого файла.
* linspace строит точные концы окна с фактическим dx не больше заданного;
  скалярные значения любых входных функций распространяются на сетку.
* Число точек проверяется до выделения массивов; входные параметры и конечность
  результатов проверяются. Отказ возвращает f=[] и failure_reason.
* Simpson накапливается по весам без матрицы «время × пространство» в обоих
  режимах. Неравномерные веса сверены с scipy.integrate.simpson.
* Параллельный solve (`n_jobs>1`) по умолчанию использует spawn и передаёт
  только численные массивы, поэтому AST-функции и локальные замыкания не нужно
  сериализовать. Streaming остаётся последовательным.
  В вызывающем скрипте для n_jobs>1 требуется стандартная защита
  `if __name__ == '__main__':`.
* Ответ проецируется на фиксированную пользовательскую target_x и возвращается
  вместе со счётчиками, временем и фактической геометрией.

## Точность и ограничения

Окно равно [problem.x_target_min−padding, problem.x_target_max+padding].
`boundary=taper` использует исходное касательное продолжение со smoothstep;
`boundary=zero` — жёсткий ноль. Линейная интерполяция требует boundary=zero.
Оба продолжения меняют пространственную схему. Размер окна нужно проверять
отдельным увеличением padding; охватить только носитель g_R недостаточно.

`boundary_state_max_abs` и `outside_query_values` — наблюдения за расчётом,
не границы ошибки. T по умолчанию вычисляется прежней формулой из tail_eps;
глобальная норма g_R в неё не входит. Явное T допускается и фиксируется.

Автоматических уточнений и сертификата полной ошибки здесь нет. Нужны отдельные
сравнения dx/2, большего окна, числа узлов, T и n либо n_steps. Увеличение
одного параметра не устраняет ошибки остальных. Условия гладкости произвольных
входных функций программно не доказываются.

Исходный решатель и его CLI `examples/solve_generated_equation.py` доступны
для сравнения. Его критерии dx/Nt тоже являются индикаторами, а не оценкой
полной ошибки конечного n.

## Сравнительный эксперимент

Драйвер `diagnostics/compare_chernov.py` выполняет явный JSON-план: отдельный
процесс на попытку, BLAS-потоки=1, без автоматических повторов. Он сохраняет
полные конфигурации/результаты, точное решение, ошибку, время загрузки и
решателя, wall time процесса, пиковый RSS через resource.getrusage, хеши до/после.
Ресурсный watchdog ограничивает конкретную серию, не математический метод.

Планы, пилоты, проверки уточнений и итоговое сравнение:
`results/chernov_integration_2026-10-18/`. Окончательные измерения выполняются
после выбора параметров; стоимость подбора хранится отдельно.
