## Сохранность алгоритмов и архитектуры

В каждом solver изменены только импорт `CauchyProblem` под `TYPE_CHECKING`

Все функции, параметры, dataclass-поля, диагностические статусы, стадии RK4,

копий с исходниками после строго перечисленных замен. SHA источников и копий
сохранены в [provenance.json](provenance.json).

RK4 остаётся классической четырёхстадийной схемой четвёртого порядка.
PI остаётся левоконцевой экспоненциальной схемой первого порядка для переменной
расширенной матрицы 3×3: `Z[k+1]=expm(h*B(x[k])) @ Z[k]`, `Z=(y,y',1)`.

`FORBIDDEN` и весь `tests/test_all_methods_remizov_pipeline.py` не изменены.
Квалифицированные имена не создают модулей верхнего уровня `rk4_solver`,
`product_integral_solver`, `dataset_loader`; прежний тест изоляции проходит.
Ремизов, Чернов, MC, безопасный загрузчик, генератор, данные, ML, старые
экспериментальные драйверы и сохранённые результаты не изменены.
`MIGRATION_MANIFEST.json` не изменён: все три файла `unchanged_mathematical_core`
по-прежнему совпадают с `source_sha256`, поэтому новая запись истории изменений
ядра не требуется. Соседний `generator_DE` не использовался.

## Фиксированный план и входы

План сохранён **до копирования solver и численных запусков** в [plan.json](plan.json).
Пять train-задач выбраны по режиму/сложности, без просмотра ошибок:
первые train-ID для constant/L1, slow_varying/L2, moderate_varying/L3,
high_contrast/L4; для oscillatory/L3 заранее выбран `AMV1_F0134_S03`, у которого
в старой серии отсутствовал R-ответ. Новых R- или MC-ответов не вычислялось.

Единственный источник исполняемых функций — существующий
`load_all_methods_equations` с явными путями из
`data/all_methods_v1_1000_2026-10-18/`. Загрузчик читает и валидирует 1000 записей,
но численные методы вызываются только для пяти перечисленных ID.

Solver передаётся исходный `equation.cauchy_problem`: его `a,b,c,g`,
`x0=-1`, `x1=1`, сохранённые `y0,v0`. Новые начальные условия не вычисляются.
Контракт передачи функций по идентичности и значений НУ проверен отдельными
тестами; `c=c_R-lambda`, `g=-g_R` сверены на реальных входах.
Публичные exact-функции используются только после возврата solver для метрик;
валидация manufactured-данных внутри прежнего загрузчика сохраняется.

Для обоих методов неизменно: `n_steps=128`, `a_min=0.001`,
`h=2/128=1/64=0.015625`, исходный интервал `[-1,1]`, 129 узлов.
Значение x=0 берётся из **точного узла 64**. Сетка NPZ из 256 точек не используется
для подстановки ближайшего отсчёта. Дополнительно вычислены ошибки на прежней
фиксированной сетке из 33 узлов `linspace(-1,1,33)`, совпадающих с каждым
четвёртым узлом новых траекторий. Интерполяция решения не используется.

Основная метрика `E0=abs(y_numeric(0)-y_exact(0))`; ε=0.05 сохранён.
Разность между `success` solver и `accuracy_met` отражена явно. Для имеющегося
MC остаётся действующее определение ошибки среднего четырёх сохранённых
ответов; прежние ML-метки и результаты не менялись.

Ресурсы: один процесс, переменные BLAS/OpenMP-потоков равны 1;
Python 3.10.11, NumPy 2.2.6, SciPy 1.15.3. Десять основных запусков: всего
2560 RK4 RHS-evaluations и 640 экспонент 3×3 для PI. Время всего отдельного
драйвера, включая загрузку, — 4.870669 с; загрузка — 3.052646 с;
кумулятивный пиковый RSS процесса — 221.078125 МиБ. Эти числа не являются
исследованием производительности методов. Индивидуальные времена, RSS и
полные dataclass-результаты сохранены в [integration.json](integration.json).

## Ошибки на фиксированной сетке 33 узлов

Здесь `E_inf` — максимум абсолютных ошибок **только на указанных узлах**,
не непрерывная верхняя граница. Относительная ошибка делится на sampled max|exact|
на той же сетке. Основной критерий сравнения остаётся E0.

| Уравнение | E_inf RK4 | E_inf PI | E_inf / max(abs(exact)) RK4 | E_inf / max(abs(exact)) PI |
|---|---:|---:|---:|---:|
| `AMV1_F0001_S00` | 2.58677823606e-09 | 0.0515616866032 | 3.5777005276e-09 | 0.071313524597 |
| `AMV1_F0060_S00` | 1.42916491863e-07 | 0.00608478235544 | 1.79040662004e-07 | 0.00762279738934 |
| `AMV1_F0122_S00` | 5.8666309144e-08 | 0.13908891997 | 4.83220649041e-08 | 0.114564285981 |
| `AMV1_F0134_S03` | 7.39218654615e-07 | 0.338745592651 | 1.14573609568e-06 | 0.525031464409 |
| `AMV1_F0192_S00` | 1.10211823201e-06 | 0.577851400766 | 1.43879038007e-06 | 0.75437191073 |

У PI максимальный дрейф третьей расширенной координаты во всех пяти основных
запусках равен 0.0. Это не сертификат точности y. Например, для constant/L1
ε достигнут в нуле, но E_inf на 33 узлах уже превышает 0.05.

**Наблюдение:** при одном заранее выбранном бюджете PI не достиг ε в нуле на
трёх из пяти задач. Численный алгоритм, шаг и ε после результата не менялись,
повторного подбора не было. Установлен первый порядок самой схемы и корректная
передача входов. Количественная причина больших ошибок каждого ID не выделена:
исследование сходимости и чувствительности задачи Коши здесь не выполнялось.
Ошибки замораживания и усиление возмущений — возможные механизмы, не доказанный
диагноз конкретных случаев. Режим constant не делает полную матрицу постоянной,
поскольку forcing g остаётся переменной функцией.

строках; производственный селектор не переобучался и не настраивался.

## Решение и следующий шаг

Интеграция завершена: обе реализации доступны отдельно, исходные алгоритмы и
защищённые компоненты сохранены. Технически можно готовить отдельное исследование
точности на всех 1000 задачах. Этот небольшой опыт не доказывает превосходство
RK4 на полном наборе и не устанавливает требуемый шаг PI.

Перед будущим массовым запуском нужно отдельно зафиксировать сетки уточнения,
бюджеты, правила отказов и сравнения E0; исследовать сходимость без подбора по
test-ответам; учитывать различие IVP и глобального контрактов. Желательно также
отдельно исправить два старых теста fixtures. Массовый расчёт и подключение к
ML этой задачей не выполняются.
