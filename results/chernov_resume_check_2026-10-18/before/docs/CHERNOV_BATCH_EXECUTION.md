# Безопасный пакетный запуск Chern

Работать из корня проекта, использовать `.venv`. Математическая схема не менялась:
`ChernovSolver.solve`, n=128, 513 узлов, dx=0.0125, padding=12, cubic+taper,
tail_eps=1e-8, n_jobs=1, проверка ошибки на 33 точках [-1,1].

## Ограничение процессов и владение запуском

Одновременно разрешён **один вычислительный worker во всём проекте**, даже если
старый план содержит `workers=8`. Глобальные блокировки контроллера и вычислительного
слота дополняют блокировку конкретного каталога. `n_jobs!=1` отклоняется; прямой
вызов внутреннего worker без guardian отклоняется.

Помимо worker существуют контроллер и отдельный малонагруженный guardian.
Guardian работает в своей POSIX-сессии, а worker с потомками — в отдельной группе.
При остановке guardian посылает группе SIGTERM, затем при необходимости SIGKILL,
и ожидает worker. Не используются широкие команды `pkill python` или PID из
старых файлов для уничтожения произвольных процессов.

Guardian независимо от потока worker наблюдает за:

- EOF управляющей трубы: аварийная смерть контроллера, включая SIGKILL;
- heartbeat контроллера: отсутствие более 5 с, в том числе SIGSTOP/зависание;
- командой остановки в каталоге текущей сессии;
- внешним разрешением владельца: срок **120 с с последнего продления**.

Контроллер сам не продлевает внешнее разрешение. Остановка Codex или закрытие
редактора не всегда завершает ОС-процесс контроллера; без внешнего продления
guardian всё равно остановит вычисление примерно за две минуты плюс завершение
группы. Сигналы SIGINT/SIGTERM/SIGHUP и `--stop` инициируют немедленную остановку.
Защитные блокировки удерживаются до завершения очистки. Worker наследует FD
вычислительной блокировки: даже смерть guardian не открывает второй слот,
пока первый worker ещё существует; внутренний контроль родителя остаётся
дополнительной защитой. Ошибка очистки явно записывается, не выдаётся за успех.

## Команды для существующей серии

Каталог результатов:

```bash
batch_results=results/chernov_solve1000_2026-10-18
```

Посмотреть сохранённые результаты и состояние блокировок, без вычислений:

```bash
.venv/bin/python -B diagnostics/run_chernov_batch.py --output-dir "$batch_results" --status
```

Остановить из другого терминала:

```bash
.venv/bin/python -B diagnostics/run_chernov_batch.py --output-dir "$batch_results" --stop
```

Также можно нажать Ctrl+C в терминале контроллера. Незавершённая задача останется
pending; уже опубликованный результат сохраняется. Команда `--stop` ждёт
подтверждения guardian; при неудачной очистке сообщает это явно. Историческое
`active.json` после SIGKILL может остаться с `finished=false`: смотрите также
guardian и фактические блокировки в `--status`.

**Только после отдельного решения продолжить эксперимент** — запуск/возобновление:

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -B diagnostics/run_chernov_batch.py \
  --output-dir "$batch_results"
```

Пока нужен расчёт, внешний наблюдатель продлевает разрешение не реже раза в минуту:

```bash
.venv/bin/python -B diagnostics/run_chernov_batch.py --output-dir "$batch_results" --keep-alive
```

Команда продления сама не запускает и не воскрешает остановленный расчёт.
Для ограниченной следующей партии можно добавить к запуску `--max-new 5`.
Не использовать `--init` для существующего каталога. После этой задачи
массовый расчёт **не возобновлялся**.

## Сохранение и продолжение

`attempts/<attempt>/result.json` публикуется атомарно после каждого уравнения;
затем `solutions/<ID>.json` и progress. Файлы результатов не перезаписываются.
Если контроллер погиб между публикацией ответа worker и checkpoint, продолжение
подхватит ответ из attempts. Завершённые записи, включая accuracy_not_met и
worker_exception, пропускаются. Оборванный запрос получает новую попытку,
старые запросы/логи остаются. Терминальные отказы автоматически не повторяются.

Исходный plan.json и его SHA-256 сохранены; прежние 694 записи продолжают
проверяться по исходному плану. Новая `safety_policy_v2.json` разрешает только
зафиксированную миграцию управляющего кода, хранит старые/новые SHA-256 и ссылки
на резервные копии. Численные источники и данные должны совпадать с прежними
хешами. Новые сессии и ответы отдельно записывают политику надзора/её хеш.
